## v1.134.0 - a frozen agent whose automatic restarts keep failing is escalated and shown loudly

(Branch `fix/stuck-escalation`, from main 9c3d88c. The version number is a placeholder: the live tree already carries uncommitted 1.132.0 / 1.133.0, so renumber when merging. `CLAUDE.md` is git-ignored and is not in the worktree: paste this entry into the live `agent-desktop\CLAUDE.md` when merging.)

**What went wrong (2026-10-20, from `stuck-turn-watchdog.log`).** `checkForStuckTurns()` / `recoverStuckSession()` restarts an agent whose turn shows no transcript growth for 180 s. For Software Engineering (session bf03fe1e, 2.1 MB) it fired 74 times between 20:01Z and about 01:00Z, roughly every 4 min, each time re-dispatching the SAME hung conversation, which hung again at once. Nothing told the owner: the UI showed only the blocked-style red "!" and a faint grey "Working... 18876s no recent output" line. The same log said every few minutes "stopEmptyDuplicateAgents: ... 3 live copies WITH conversations ... left alone, needs a human", also never surfaced. The transcript's last real entry was a tool_result at 22:58 local; later writes were only `queue-operation` lines (messages queued behind the hang), which bump the file's mtime.

**What changed.**
- `src/stuckEscalation.js` (new, pure logic, injected side effects):
  - Progress signal `lastRealProgressFromLines()`: only an assistant entry or a user entry carrying a `tool_result` counts. `queue-operation`, attachments, human prompts and unparsable lines do NOT. `archive.js getLastRealProgressMs(sessionCwd)` reads the tail (1 MB, then 8 MB) of the newest transcript.
  - Loop detection: when the watchdog would recover an agent, `evaluate()` first counts the recoveries since the last real progress. 3 of them = **stuck-failing**; the 4th trigger no longer re-dispatches.
  - Escalation (`tick()`, run at the start of every watchdog pass): once per episode, at most once per 30 min per agent, never when real progress was seen in the last 10 min, it closes the doomed session and starts a FRESH one in the agent's folder (`stopBackgroundAgentForCwd` then `dispatchBackgroundAgent({forceFresh, initialPrompt})`, no `--resume`, then attaches). The first prompt says: read `<agent folder>\handoff_latest.md` and continue from its EXACT NEXT STEP (or says there is no handoff file). If the fresh session shows no real progress within 10 min, or cannot be started, it is logged and the state stays up: no further automatic restarts.
  - Loud: the OS notification fires on entering the state and again every 30 min; a question is written to `<root>\shared_state\open_questions\` in the same file format `shared_tools\ask_iddo.py` writes (so the "waiting for you" bar lists it) and is resolved automatically when the agent shows real progress. The duplicate-copies condition ("N live copies WITH conversations") is surfaced the same way (notification, question, one plain line) and clears when the sweep sees fewer than 2.
  - Every decision is logged to `stuck-turn-watchdog.log` (`STUCK-FAILING ...`, `escalating ...`, `fresh session started ...`, `cleared ...`).
- UI (`src/renderer/stuck-alert.js`, `styles-stuck-alert.css`): red pill in the agent list "STUCK 5 h - auto-restart failed" (amber "has 3 live copies - needs a person" for duplicates) and the same text, red, in the chat header line that normally shows "Working...". Distinct from the blocked "!" (blocked = waiting for a person, stuck = frozen). New IPC: `stuck-state` event, `get-stuck-states`.
- Wiring in `src/main.js`: `stuckEsc` (create), `escalateStuckAgent()`, `recordRecovery` in `recoverStuckSession`, `evaluate`/skip in `checkForStuckTurns`, `setDuplicates` in `stopEmptyDuplicateAgents`.

**Not done / limits.** State is in memory only (an app restart forgets an episode; the question file is resolved by text when the agent recovers). Only the live copy that `stopBackgroundAgentForCwd` finds first is stopped on escalation; other live copies are left (and flagged as duplicates). The visual badge was not checked in a running sandbox instance.

**Review fixes (same version, before merge).**
- Loop detection has NO time window any more: 3 recoveries since the last REAL progress (reset only on progress) declare stuck-failing, so a 5-8 min cadence counts too. Progress 0/null is UNKNOWN: never declares a failure, never wipes the history, never escalates. `getLastRealProgressMs` takes the max over the newest 2 transcript files.
- A stuck-failing agent is SKIPPED by the watchdog (no restarts of any kind) until it shows real progress or a person acts (Restart Session, + New chat, pause or delete).
- Fleet protection: if more than 2 agents are stuck-failing at once, nobody is escalated and ONE plain "Several agents are frozen at the same time (API or network?)" alert is raised (notification + waiting-bar question, cleared when the count drops to 2). Global cap on escalations: 1 per 5 min and 2 per hour across all agents. The fresh dispatch is NOT urgent (it goes through the CPU-guard start limiter).
- `escalateStuckAgent` guards: refuses test-mode without live-agent permission, a missing agent folder, a paused or unlisted agent, and a restart placeholder already in flight (it never overwrites one). `tick()` re-checks at escalation time that the agent still has an attached session, is still working and is not approval-blocked. It stops ALL live copies of the folder (fresh listing), verifies none remain, and otherwise aborts and keeps the alert. Removed or paused agents lose their stuck and duplicate state. The duplicate-copies alert needs 2 sweeps in a row. The handoff path in the fresh prompt is in single quotes.
- Tests: `tests/stuckEscalation.test.js` now 31 (adds the cases above, plus real-file tests of `getLastRealProgressMs`: tail read, 1 MB to 8 MB fallback, cut first line, queue-only newest file). The `escalateStuckAgent` guards are asserted by a source check because that function needs electron.
